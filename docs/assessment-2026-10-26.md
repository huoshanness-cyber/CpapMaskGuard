# CpapMaskGuard 全方位评估与建议（2026-10-26）

> 评审人：Claude Opus 5.5（只读评审，未改任何代码）
> 评审范围：`main@2dfa1ad`（Android 首发）＋ `cursor/ios-foreground-monitor-0b7f@174a760`（iOS 0.3.9，远端最新）
> 验证：iOS 0.3.9 模拟器 `xcodebuild build` 通过（仅 2 条 `videoOrientation` 弃用警告）；本机无 JDK，Android / `detector-core` 单测**未能运行**。
> 文中「已拍板」指象总已定的产品决策：本机对准门控后再上云；连续 10 张 MASK_OFF 停云上传但报警不停；每天可恢复上传 10 次；回传小象腾讯云；官网页脚中文镜像下载；开源后续可能自带免费 Key。

## 1. 总评

**一句话：方向对、底子扎实，但离“敢让陌生人整夜依赖”还差三件事——不能静默失效、Key 不能进安装包、上云必须先过门控。**

- **定位成立。** 夜里无意识摘面罩是 CPAP 依从性的真实痛点；“免费、开源、中文、安卓可后台”在同类里有差异化。免责声明（非医疗器械）两端都有，措辞克制，保持。
- **架构选型合理。** 云端 MiniMax-M3 做主判、本机 MobileNetV3 embedding / 灰度做兜底（仅安卓）、本机听鼾做辅助信号；`detector-core` 抽成纯 Kotlin 模块且有单测；两端提示词与请求参数刻意对齐（thinking 关、detail low、temperature 0.1、max 64 tokens）。这些都是对的。
- **最大风险是“静默失效”，而不是误报。** 对一个安全提醒类工具，“以为在守护、其实早停了”比多响一次严重得多。目前两端都存在这种路径（详见 §2.1）：
  - iOS：只要应用短暂进入 `.inactive`（下拉控制中心、来电横幅、低电量弹窗），监测循环就退出且不再重启，界面却仍显示“守护中”。
  - iOS：断网 / 云端报错时没有任何本机兜底，也不提醒，只在内存日志里记一笔。
  - 安卓：进程被杀后 `START_STICKY` 重启，但 Android 11+ 不允许从后台启动的前台服务使用相机 / 麦克风，重启后大概率开不了相机，而当前的失败上报方式（后台拉起邮件选择器）在夜里同样会被系统拦截。
- **费用模型目前不可持续。** 按默认 8 秒一张、一晚 8 小时，每用户每晚约 3,600 次调用，估算 **¥3.5–8.8 / 人 / 晚**（§2.4）。“自带免费 Key”在门控和服务端配额落地之前**不能发**。
- **已拍板的 6 项决策，代码里一项都还没实现**（全仓检索不到门控、配额、腾讯云、上传计数相关代码）。这本身不是问题，但意味着下一阶段的工作量主要在这里，且需要两端共用一份状态机规格。
- **分支状态需要收口。** `main` 只有首发提交；iOS 三个迭代都在 `cursor/*` 分支上。你本机的 `cursor/ios-foreground-monitor-0b7f` 比远端落后 1 个提交（`174a760`），工作区里是等价的未提交改动加一份重新生成的 `project.pbxproj`。

## 2. 分领域建议（按优先级）

优先级定义：**P0** = 发给更多测试者或发免费 Key 之前必须做；**P1** = 下一个版本内做；**P2** = 稳定后做；**P3** = 探索。

### 2.1 可靠性（误报 / 补光 / 保活 / iOS 亮屏限制）

| 优先级 | 问题 | 证据 | 建议 |
|---|---|---|---|
| P0 | **iOS 假守护**：`stillGuarding()` 要求 `applicationState == .active`，`RootView` 只在 `.background` 时调用 `leaveForeground()`。应用一进 `.inactive`，`runMonitor` 就 `return`，`phase` 仍为 `.guarding`，回到 `.active` 后无人重启循环；相机和白屏继续开着、但不再拍照判定。 | `GuardModel.swift` `stillGuarding` / `runMonitor`；`RootView.swift` `onChange(of: scenePhase)` | `.inactive` 时暂停而不是退出；回到 `.active` 时若 `phase == .guarding` 就重启循环。加一个“看门狗”：主屏显示“上次判定 N 秒前”，超过 3 个间隔未出新结果即标红并震动。真机验证用例：守护中下拉控制中心 5 秒再收起，确认继续出新结果。 |
| P0 | **iOS 云端失败无兜底、无提醒**：没 Key / 断网 / HTTP 错误时只记日志；连续 5 次失败也只是一条日志。 | `GuardModel.swift` `noteRoundError` | 连续失败达到阈值（建议约 30 秒内 3 次）时，发出一种**区别于脱落铃声**的“守护失效”提示音＋通知，并在主屏显示原因。iOS 本机兜底（见 2.2）落地前，这是唯一的安全网。 |
| P0 | **安卓进程被杀后的恢复是假的**：`START_STICKY` 重启时应用在后台，Android 11+ 不允许后台启动的前台服务使用相机 / 麦克风；失败后的 `LogMailer.sendLogEmail` 会从 Service 拉起邮件选择器，Android 10+ 后台启动 Activity 也会被拦截。 | `MonitorService.kt` `onStartCommand` / `ensureLoop`；`LogMailer.kt` | 重启后检测到相机绑定失败时，改为发一条**高优先级、可全屏的“守护已中断，点此恢复”通知**（带声音），不要拉起邮件。把“被杀 / 中断”作为事件写入遥测（见 2.5）。 |
| P0 | **安卓断网时每帧多等最长 12 秒**：每张图先等云端超时，再走本机兜底，报警时延会被拉长到“间隔 + 12 秒 + 本机推理”。 | `CloudMaskDetector.kt` 超时常量；`MaskDetector.decideBitmap` | 加熔断：连续 2 次云端失败后，接下来 N 分钟本机优先，后台低频探测云端恢复。 |
| P1 | **单帧 MASK_OFF 即响铃**（`DEBOUNCE_CONSECUTIVE = 1`）。这是有意的时延取舍，但目前没有任何数据能说明误报率是多少。 | `DetectionConfig.kt`；`MonitorLogic.swift` `Debouncer` | **先不改阈值**，先补数据：停止铃声时给两个按钮“确实脱落 / 误报”，结果进遥测。积累约两周数据后再决定是否改成 2 帧确认，或只在本机兜底路径上用 2 帧。 |
| P1 | **只凭听鼾就报警**：相机说“戴着”时，持续打鼾 12 秒仍会报警。同床伴侣打鼾、呼吸机本身的气流声都可能触发。 | `SnoreFusion.kt` / `MonitorLogic.swift` `SnoreFusion` | 保留功能，但在报警原因里明确标“由鼾声触发”，并单独统计“鼾声触发 + 用户标误报”的比例；数据不好就把“相机说戴着时的纯鼾声报警”改成默认关闭。 |
| P1 | **iOS 整夜亮屏**：前摄白屏默认 85% 亮度对着脸，影响睡眠和同床的人；OLED 有烧屏和发热风险；没有充电 / 温度检查。 | `GuardModel.init` 默认值；`HealthMath` 温度项固定为 70 | 开始守护前检查是否在充电（未充电时警告）；用 `ProcessInfo.thermalState` 替代固定温度分；引导用户开“引导式访问”（防止误退出）和“勿扰 / 专注模式”（减少来电横幅导致的 `.inactive`）。用现有的 `CpapLightTest` 测出云端仍能判准的**最低亮度**，并试验暖色 / 红色补光是否可用。 |
| P1 | **iOS 侧边音量低就听不见铃声**，应用无法强制改系统音量。 | `NightAudio.swift`；README 第 7 条 | 开始守护时音量低于 50% 应**拦一下**（要求用户确认），而不是只显示一行警告。长期可评估向 Apple 申请 Critical Alerts 权限（健康类有机会获批，但不保证）。 |
| P2 | “画面无人”长时间持续（手机被碰歪、人去了别处）目前只显示“请先摆好手机”。 | `MonitorService.handleDecision` | 这一项由本机门控统一承担（见 2.2）：连续 N 分钟门控不过，震动＋通知“手机可能被碰歪了”。 |

### 2.2 技术架构（安卓 / iOS / MiniMax / 本机门控 / 听鼾）

**P0 · 先写一份两端共用的“上云策略状态机”规格，再动手实现。** 已拍板的门控、连续 10 张暂停、每日 10 次恢复，本质上是同一个状态机。建议的状态与转移：

```
GATING（本机门控评估）
  └─ 门控通过 ─→ CLOUD_ACTIVE（正常上云）
CLOUD_ACTIVE
  ├─ 云端 MASK_ON ─→ 连续 OFF 计数清零
  ├─ 云端 MASK_OFF ─→ 计数 +1（第 1 张即按现有规则报警）
  └─ 计数达到 10 ─→ CLOUD_PAUSED（停上传，报警不停，直到用户手动停）
CLOUD_PAUSED
  └─ 恢复触发（见 §5 第 3 问）且今日恢复次数 < 10 ─→ 次数 +1 ─→ CLOUD_ACTIVE
     恢复次数已满 ─→ LOCAL_ONLY（今晚只用本机兜底 + 听鼾，主屏常驻提示）
```

规格里必须写清的细节：
- **UNCERTAIN / NO_PERSON 对连续计数的影响。** 建议：两者都不加计数、也不清零，只有 MASK_ON 清零。
- **“每天”的边界。** 不要用 0 点：一晚跨越 0 点，会在半夜突然重置配额。建议用**本地时间中午 12:00** 作为“睡眠日”分界。
- **计数以服务端为准**（防止改本地时间或重装绕过），本机只做缓存和离线时的保守估计。
- 规格附一份 **JSON 测试向量**（输入事件序列 → 期望状态 / 是否上传 / 是否报警），Kotlin `detector-core` 和 Swift `MonitorLogic` 用同一份向量跑单测。暂时不必上 KMP 共享代码。

**P1 · 本机对准门控（Gate）怎么做：**
- 目标有两个：①**省钱**，没对准、全黑、过曝、模糊、画面没变化的帧不上云；②**交互**，开始守护时实时告诉用户“太暗 / 没看到人 / 手机歪了”。
- 信号建议按成本从低到高组合：亮度均值与方差（已有 `LumaStats`）→ 清晰度（拉普拉斯方差）→ 与上次上云帧的差异（下采样灰度差）→ 人体 / 头部是否在画面中（iOS 用系统 Vision 的人体和人脸检测，免费且在本机；安卓不要依赖 Google Play 服务，国内机型没有，改用随包的 MediaPipe 人脸检测 tflite，Apache-2.0）。
- **关键陷阱：戴全脸面罩时人脸检测经常失败。** 门控不能把“检测到人脸”作为必要条件，否则正好在戴着面罩时不上云。规则应是“检测到人体 / 头部，**或**画面与校准基准足够相似”即通过。
- **拿不准时放行上云**（宁可多花钱，不可漏判），只对明确的全黑 / 全白 / 严重模糊拒绝。
- “画面没变化”的跳过要设心跳：上次结果是 MASK_ON 且画面稳定时，最多跳过约 60 秒必须再上云一次。摘面罩本身就是画面变化，会立即触发上传。

**P1 · iOS 需要最小本机兜底。** 安卓的 embedding 方案（MobileNetV3-Small + 两类聚类）可以用 Core ML 移植；在此之前，至少做到门控 + 听鼾 + “云端失效”提醒。

**P1 · MiniMax 调用：**
- 从响应的 `usage` 字段读真实 token 数并记录（目前两端都忽略了 `usage`），这是费用估算唯一可靠的依据。
- 给提示词加版本号（例如 `prompt_v1`），随遥测上报，改提示词时可以做 A/B。
- 端点和模型名做成远程配置：境外用户走国际端点（`api.minimax.io`），并可切换到更便宜的 `MiniMax-M3.1-Flash`（官方价 ¥1 / ¥4 每百万 tokens，约为 M3 的一半），前提是先在评测集上验证准确率（见 2.7）。

**P2 · 代码健康：**
- `MainActivity.kt` 有 1,229 行，后续按“主屏 / 设置 / 烤机”拆分，但不要和 P0 一起做。
- 版本号两端不一致（安卓 0.3.7 / versionCode 19，iOS 0.3.9 / build 3），建议统一成“产品版本 + 平台 build 号”。
- `FrameCapture.swift` 用了 iOS 17 起弃用的 `videoOrientation`，换成 `videoRotationAngle`。
- README 写的本机兜底是 “EfficientNet-Lite0 二分类”，实际是 **MobileNetV3-Small embedding + 最近簇比较**（见 `assets/MODEL_SOURCE.txt`、`MaskDetector.kt`）。文档要以代码为准。

### 2.3 产品与交互

| 优先级 | 建议 |

| P2 | **温和升级报警（可选）**：先震动 3 秒再响铃，照顾同床的人；默认仍保持立即响铃。 |

### 2.4 费用与配额

**单价（MiniMax 开放平台国内站，2026-10 标准档、已含五折）：** MiniMax-M3 输入 ¥2.10 / 百万 tokens，输出 ¥8.40 / 百万 tokens；MiniMax-M3.1-Flash 输入 ¥1.00、输出 ¥4.00。价格会变，上线前以官网为准。

**单次调用估算：** 文本提示约 130 tokens；`detail: low` 的 640px 图片 token 数官方未明示，暂按 300–1,000 估；输出是一个标签，约 3–8 tokens。合计每次约 ¥0.0010–0.0024。

| 场景 | 每晚调用次数（8 小时） | 每用户每晚 | 每用户每月（30 晚） |
|---|---|---|---|
| 现状：8 秒一张、全部上云 | 3,600 | ¥3.5–8.8 | ¥105–263 |
| 门控后（估计约 80 次/小时：变化触发 + 60 秒心跳） | 约 640 | ¥0.6–1.6 | ¥19–47 |
| 门控后 + 换 M3.1-Flash（需先验证准确率） | 约 640 | ¥0.3–0.8 | ¥9–23 |

结论与建议：
- **P0** 先在两端记录真实 `usage.prompt_tokens`，一周后用真实数据替换上表的估算区间。
- **P0** 免费 Key 的前置条件：服务端中转 + 每设备每晚硬上限（建议先按约 1,500 次/晚）+ 全局月预算上限 + 远程一键关停。全局预算用完时，客户端自动降级为“仅本机”，并明确告诉用户。
- 已拍板的“连续 10 张 MASK_OFF 停上传”主要省的是“人醒着、不戴面罩”的那段；**“人离开床、画面全空”整夜上传的浪费要靠门控省**，两者缺一不可。

### 2.5 数据回传（小象腾讯云）

**P0 · 一个服务，三个职责：**
1. **识别中转** `/v1/classify`：MiniMax Key 只存在服务端；服务端执行配额（每日恢复次数、每晚调用上限），返回标签和 usage。
2. **遥测** `/v1/telemetry`（批量上报）：只传指标，**默认不传图片**。
3. **远程配置** `/v1/config`：关停开关、模型 / 端点、抓拍间隔、提示词版本、门控阈值、最新版本号（供安卓检查更新）。

**遥测事件建议（全部不含图片）：** 守护开始 / 结束（时长、补光模式、机型、系统版本、App 版本）；每次云端调用（时延、标签、usage、错误码、提示词版本）；门控决策（通过 / 拒绝及原因的计数，按分钟聚合）；报警（触发来源：相机 / 鼾声、到停止的时长、用户反馈“戴好了 / 误报”）；失效事件（`.inactive` 中断、前台服务被杀、相机绑定失败、连续失败）；状态机转移（暂停、恢复、配额用尽）。

**工程要点：** 设备标识用安装时随机生成的 ID，不采集 IMEI / IDFA；本机先落盘、联网再批量上传，失败可重试；数据存放在境内地域；原始事件保留 90 天，聚合数据长期保留；中转服务挂掉时，客户端必须能降级到本机判定并提示用户，**报警链路不能只依赖中转**。

**图片回传（用于做评测集、训练本机模型）：** 只能是**单独开关、默认关闭、单独同意**；存 COS 时设生命周期自动删除；在隐私政策里写明用途和期限。是否做，见 §5 第 2 问。

### 2.6 隐私与合规

| 优先级 | 问题 | 建议 |
|---|---|---|
| P0 | 卧室里的人脸照片，加上“使用呼吸机”这一健康信息，在《个人信息保护法》下属于**敏感个人信息**，需要单独同意、明确告知接收方（MiniMax，以及回传后的小象）、用途和保存期限。 | 首次上云前弹出单独同意页（可拒绝，拒绝后走仅本机）；官网发布隐私政策；App 内可随时撤回。 |
| P0 | 安卓首启文案与实际行为不符（见 2.3）。 | 同上，并补“仅本机”开关。 |

## 3. 给实现者「科学怪人」的指挥清单

> 原则：一步一个 PR，每步可单独验证；不要把 P0 和重构混在一起；凡涉及判定和报警的改动，必须附真机验证记录（机型、系统版本、步骤、结果）。

**第 0 步 · 收口分支（无功能改动）**
1. 把本机 `cursor/ios-foreground-monitor-0b7f` 对齐到远端 `174a760`（工作区里是等价改动和一份重新生成的 `project.pbxproj`，**先跟敏敏确认再丢弃**）。
2. 把 iOS 0.3.7 → 0.3.9 三个分支按顺序合进 `main`，之后所有工作从 `main` 拉分支。

**第 1 步 · iOS 不再假守护（P0）**
1. 让 `.inactive` 只暂停循环，回到 `.active` 且仍在守护时自动重启循环；`.background` 维持现有的停止逻辑。
2. 主屏加“上次判定 N 秒前”；超过 3 个抓拍间隔没有新结果时标红并震动。
3. 真机验证：守护中分别下拉控制中心、下拉通知中心、接一个来电，各持续 5–10 秒，确认回来后仍持续出新结果。

**第 2 步 · 两端“守护失效”提醒（P0）**
1. 定义统一的失效条件：约 30 秒内连续 3 次判定失败，或相机绑定失败，或循环停止超过 3 个间隔。
2. 触发时：一种区别于脱落铃声的提示音 + 高优先级通知 + 主屏原因。
3. 安卓：被杀重启后相机绑定失败时，改发“守护已中断，点此恢复”的全屏通知；删掉 Service 里自动拉起邮件的调用。
4. 安卓：云端熔断（连续 2 次失败后本机优先 N 分钟，后台低频探测恢复）。
5. 真机验证：开飞行模式 60 秒；安卓用 `adb shell am kill` 模拟被杀。

**第 3 步 · 记录真实用量（P0，改动小）**
1. 两端解析响应里的 `usage`（输入 / 输出 tokens），写进日志和每轮记录。
2. 连续一周收集真实数据，替换 §2.4 的估算区间。

**第 4 步 · 小象腾讯云中转 + 配额 + 远程配置（P0）**
1. 服务端：`/v1/classify`（持有 Key、执行每设备配额、返回标签 + usage）、`/v1/telemetry`、`/v1/config`（关停开关、模型、端点、间隔、提示词版本、门控阈值、最新版本号）。
2. 设置全局月预算上限，超出时 `/v1/config` 下发“仅本机”。
3. 客户端：官方构建只走中转；源码构建保留“自带 Key”直连作为开发者模式；中转不可用时降级本机并提示。
4. 确认 Key 不再出现在 APK / IPA 中（解包检查一次，结果写进 PR 描述）。

**第 5 步 · 合规最小集（P0）**
1. 首次上云前的单独同意页（可拒绝）；设置里加“仅本机”开关；改正安卓首启文案。
2. iOS `MaskFrames` 设置为不进备份。
3. 删除代码里的个人邮箱；README 删除个人姓名。
4. 起草隐私政策（交给合规审），放到官网。

**第 6 步 · 上云策略状态机（P0/P1）**
1. 先提交规格文档（状态、转移、计数规则、睡眠日边界、服务端为准）和 JSON 测试向量，**等象总确认 §5 第 3 问后再实现**。
2. 在 `detector-core` 和 iOS `MonitorLogic` 中分别实现，两边用同一份测试向量跑单测。
3. 主屏常驻显示：今晚云端状态（正常 / 已暂停 / 仅本机）和剩余恢复次数。

**第 7 步 · 本机对准门控（P1）**
1. 亮度 / 方差 → 清晰度 → 帧差 → 人体 / 头部检测，按此顺序组合；拿不准时放行。
2. **不能把检测到人脸作为必要条件**（全脸面罩会让人脸检测失败）。
3. 帧差跳过要有 60 秒心跳上限。
4. 开始守护先做对准检查，失败时实时提示具体原因。
5. 用评测集验证：门控拒绝的帧里，不能出现真实 MASK_OFF。

**第 8 步 · 数据闭环（P1）**
1. 报警页：触发帧缩略图 + “我戴好了 / 误报”按钮，结果进遥测。
2. 遥测事件按 §2.5 实现，默认不含图片。
3. 建立评测集和离线评测脚本；加 GitHub Actions CI。

**第 9 步 · 分发（P1）**
1. 安卓正式签名 keystore（离线保存），后续只发正式签名包。
2. GitHub Releases + 官网镜像（同文件、同 SHA-256）；安卓 App 内版本提示。
3. 补 `SECURITY.md`、`NOTICE`；README 与代码对齐。

## 4. 不要改的

- **云端为主、本机兜底的总体结构**（安卓），以及两端对齐的请求参数：MiniMax-M3、thinking 关、detail low、temperature 0.1、max 64 tokens、相同提示词。要改只能通过“提示词版本 + 评测集”走。
- **标签解析先判 MASK_OFF 再判 MASK_ON** 的顺序。
- **NO_PERSON 不报警**；**铃声必须手动停**，停后有约 2 秒安静期；守护在报警后继续。
- **安卓报警链路**：闹钟音频流、临时拉满闹钟音量并在结束后恢复、全屏通知、点亮屏幕。
- **iOS 只做前台监测的诚实表述**，不要尝试任何“后台偷开相机”的做法（审核会拒，也不可靠）。
- **开发期的 Key 注入方式**（gitignore 的 `local.properties` / `Secrets.xcconfig`）以及错误信息里的 Key 脱敏。
- **0.3.8 的设置页闪退修复**（导航目标页上单独注入 `GuardModel`）。桌面上 6 份 `.ips` 都是同一个 `EnvironmentObject.error()` 崩溃，不要回退。
- **音频从不上传；听鼾失败不影响拍照**。
- **健康分只做提示、不强制停止守护。**
- **`detector-core` 纯 Kotlin 且带单测** 的分层；新增的判定 / 策略逻辑继续放这里。
- **已拍板的 6 项产品决策**：按决策实现，不要在实现中途改变语义。
- **MIT 许可证**。

## 5. 需象总拍板的问题

1. **免费 Key 的预算与上限。** 建议：门控和服务端中转上线前不发免费 Key；上线后设全局月预算上限（金额请象总定），每设备每晚硬上限先按约 1,500 次；预算用完时自动降级为“仅本机”并告知用户。请确认月预算金额，以及预算用完时是“降级仅本机”还是“停止新用户领取”。
2. **回传小象腾讯云是否包含图片。** 建议：默认只传指标（不含图片）；图片只作为“单独开关、默认关闭、单独同意”的自愿捐赠，用于评测集和本机模型训练，按期自动删除。请确认是否要做图片捐赠，若做，保存多久。
3. **“恢复上传”由什么触发。** 选项：A. 用户在报警页点“我戴好了”（明确、可控，建议作为主路径）；B. 本机门控检测到画面明显变化后自动恢复（无感，但可能在用户未戴回时就消耗一次额度）；C. 两者都算。建议选 C，但 B 需连续多帧确认才计一次。同时请确认：10 次恢复用完后，当晚是否只靠本机兜底和听鼾继续守护（建议是，并在主屏常驻提示）。
